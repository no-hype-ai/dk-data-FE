# Implementation Plan: Observability & Platform Governance

**Branch**: `013-observability-governance` | **Date**: 2026-02-15 | **Spec**: [spec.md](spec.md)

## Summary

Deploy existing ServiceMonitor and PrometheusRule manifests to enable Grafana dashboard data, add PostgREST health probing, implement a two-layer audit trail (FastAPI middleware + PostgreSQL trigger), build a lightweight migration runner with tracking table, and establish data classification with retention policies. Resolves GitHub Issues #91, #17, #9, #18, #19.

## Key Technical Decisions

### US1: ServiceMonitor Deployment
- Existing manifests in `k8s/base/service-monitor.yaml` and `k8s/base/alert-rules.yaml` are already registered in kustomization.yaml
- Labels use `release: mimir` for Prometheus Operator discovery — verify against dk-alchemy cluster config
- PostgREST ServiceMonitor scrapes at `/` — may need path update to `/health` if root doesn't serve Prometheus format
- CronJob PodMonitor selects `app.kubernetes.io/component: batch-job` — verify CronJob pod templates have this label

### US2: PostgREST Observability
- Use Prometheus Probe CRD targeting PostgREST `/health` endpoint (if blackbox-exporter exists in cluster)
- Fallback: Update existing PostgREST ServiceMonitor to scrape `/health` with appropriate content-type handling
- PostgREST v12.2.3 health endpoint returns JSON with connection pool status — parseable by blackbox HTTP probe

### US3: Audit Trail Architecture
- **Job-trigger (FastAPI)**: New `AuditLoggingMiddleware` inserted into existing middleware stack after `RequestTrackingMiddleware` — captures HTTP context, JWT identity, response status
- **PostgREST (database-level)**: PostgreSQL trigger function on `api.*` views using `current_setting('request.jwt.claims')` to extract JWT role/sub at database level
- **CronJobs**: Extend existing `meta.refresh_log` writes to also insert into `meta.api_audit_log` with `source='cronjob'`
- All audit writes are async (background task) to avoid blocking API responses
- New `api.audit_log` view with `api_user`-only access for compliance queries

### US4: Migration Runner
- Custom Python script (`run_migrations.py`) using psycopg2 — ~100 lines
- Creates `meta.schema_migrations` tracking table on first run
- `--baseline` flag marks all existing migrations as applied without executing
- Sorts migrations by numeric prefix, computes SHA-256 checksums
- Integrated into `db-init-job.yaml` as final step after schema/role/view creation
- Halts on first failure, reports error, does not mark failed migration

### US5: Data Classification & Retention
- `meta.data_classification` table seeded with classifications for all ~60 tables
- 4 tiers: `public`, `internal`, `pii`, `confidential`
- PII tables: `raw.orcid` (researcher names, affiliations)
- Confidential tables: `scoring.*`, `mart.*`, `staging.hospitals/certifications/tavr_volumes`
- Extend `purge_history.py` to read retention_days from `meta.data_classification` and purge across multiple tables
- Add `retention_days` column to `meta.data_sources` for per-source override
- `docs/DATA_CLASSIFICATION.md` as human-readable reference
