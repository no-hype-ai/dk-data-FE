## Key Technical Decisions

### D1: Dockerfile Fix Strategy
Remove `COPY --from=builder /build/src/dk_data /app/dk_data` (line 26) and `ENV PYTHONPATH=/app` (line 29). The `pip install .` in the builder stage already installs the package to site-packages. Also fix `fetch_data.py` and `fetch_molecules.py` to use absolute imports (`from dk_data.ingestion.fetchers import ...` instead of relative imports via `sys.path.insert()`).

### D2: API View Approach
- 2 views already complete (competitive_landscape, molecule_properties) — no changes needed
- 1 view needs API view only (bioactivity) — add to db-init-job.yaml
- 1 view needs API view for existing table (sider) — add to db-init-job.yaml
- 1 view needs placeholder update (patents) — update in db-init-job.yaml to reference silver.patents
- 3 views need new tables + views (company_pipeline, trial_publication_features, targets) — migration 065 + db-init-job.yaml

### D3: Data Source Pattern
Use BaseFetcher pattern (same as PR #87's 14 CI sources). Do NOT use the legacy BaseAPIClient/RawIngestionService pattern. The existing API clients (uniprot_client.py, rcsb_pdb_client.py, orcid_client.py) are reference implementations but the fetchers will use direct HTTP via the BaseFetcher session.

### D4: ORCID Raw Table
ORCID needs a new raw table (`raw.orcid`) since none exists. UniProt and PDB already have raw tables from migration 028. Migration 066 creates the ORCID table.

### D5: Lock File Strategy
Use `uv lock` to generate `uv.lock` from pyproject.toml. Add upper version bounds to all dependencies (e.g., `psycopg2-binary>=2.9.9,<3.0`). The Dockerfile already references `uv.lock*` so it's pre-wired for this approach.
